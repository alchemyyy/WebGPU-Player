WebGPU Player

Codec vectors

A codec vector is a known input with a known answer. Qualification vectors ship to the browser, where the capability probes check decoders against them before a route is advertised. Test vectors only feed tests and generators.

The generators are Python 3.10 or later, in scripts/codec_vector_assets/, with their tests in scripts/codec_vector_assets/test/. They write the committed bin/codec_vector_assets/, except the local playback media generators, which write the ignored bin/playback_smoke_media/. A generate_ script makes its output from nothing but the repository and FFmpeg, while a create_ script derives it from media you supply. Hand-made vectors live in src/capability/vectors/.

Generate or check everything

From the engine root:

python scripts/generate_all_codec_vector_assets.py            # Writes bin/codec_vector_assets/
python scripts/generate_all_codec_vector_assets.py --check    # Fails unless every committed asset matches
python -m unittest discover -s scripts/codec_vector_assets/test -p "*_test.py"

generate_all_codec_vector_assets.py runs every generator of committed assets in order, and passes --regenerate-sources to the TrueHD generator so its source streams are re-encoded and compared too. It continues past a failure and exits with status 1 if any generator failed. It does not run the local playback media generators.

bin/codec_vector_assets/ is the one committed folder in bin/, so every change to an asset shows in review. .gitattributes stores it without line-ending conversion, so the committed bytes are the generated bytes.

Every committed asset reproduces with FFmpeg and FFprobe 2026-03-01-git-862338fe31-full_build-www.gyan.dev on PATH. The HEVC range-extension and AV1 Dolby Vision generators refuse any other build. The MPEG-2 vector was first encoded by Jellyfin FFmpeg 8.1.2, which writes the same bytes. Pass another executable to its generator with --ffmpeg.

Two helpers serve them: generated_output.py (shared write, check, and install helpers) and engine_layout.py (the engine’s folders, read from tools/constants.json through tools/constants.py). The DTS and TrueHD generators compute the TypeScript import paths they embed from the same constants, so moving a folder only needs a rerun.

The engine imports the two generated TypeScript modules as #codec_vector_assets/*, and scripts/library-assets.mjs serves the qualification streams.

The generators work in one of three modes:

  • Deterministic generators rewrite their output, and with --check fail when a committed file differs from a fresh run: the DTS and TrueHD modules, and the 7.1 downmix reference.
  • Encoder-dependent generators compare a fresh encode with the committed bytes: the JPEG 2000 and MPEG-2 vectors, and the TrueHD source streams under --regenerate-sources. Another encoder build writes different bytes, so a differing encode never replaces a committed asset, while a missing one is installed. With --check, a missing asset fails as well.
  • The HEVC range-extension and AV1 Dolby Vision generators refuse any FFmpeg build but the pinned one. Before writing each encode the HEVC generator checks the access-unit lengths, the picture types, the profile and constraint flags of the VPS and SPS, and the decoded fingerprints. The AV1 Dolby Vision generator runs the checks listed in AV1 Dolby Vision vectors.

HEVC range-extension vectors

These Annex B files are deterministic WebCodecs capability probes. They are 192x192, because common NVIDIA HEVC decoders reject smaller coded sizes. They prove only that the exact codec configuration decodes, copies to the expected WebCodecs raw format, and produces the expected fingerprints. They prove nothing about performance, resolution or level limits, seeking, or transport.

Toolchain: FFmpeg 2026-03-01-git-862338fe31-full_build-www.gyan.dev, libavcodec 62.24.100, libx265 4.1+225-1b48507eb.

The source is FFmpeg testsrc2 at 192x192 and one frame per second. Each of the nine vectors is one IDR access unit followed by one P access unit, which qualifies general inter decode for the exact tuple.

Every vector uses these x265 settings, serial because there is no thread pool and one frame thread:

-preset fast -crf 32
-x265-params info=0:pools=none:frame-threads=1:wpp=0:log-level=error:keyint=30:min-keyint=30:scenecut=0:bframes=0:repeat-headers=1

info=0 prevents the x265 user-data SEI, so nothing is stripped after encoding. For example:

ffmpeg -f lavfi -i "testsrc2=size=192x192:rate=1:duration=2" \
  -frames:v 2 -pix_fmt yuv422p10le -c:v libx265 \
  -profile:v main422-10 -preset fast -crf 32 \
  -x265-params "info=0:pools=none:frame-threads=1:wpp=0:log-level=error:keyint=30:min-keyint=30:scenecut=0:bframes=0:repeat-headers=1" \
  -f hevc -y main422-10.hevc

After each encode the generator rewrites the profile, tier, and level fields of the VPS and SPS, removing and reinserting the emulation-prevention bytes around the rewritten RBSP:

  • Level: every vector signals Level 3.1 (general_level_idc 93). x265 gets no level-idc, because with CRF it would enforce the level through VBV, which it reports as non-deterministic. Without it x265 signals Level 1 and the slices are byte-identical, so the generator writes 93 instead.
  • Profile: x265 does not emit general profile IDC 4 for 4:2:0 at 8 or 10 bits, so for rext420-8 and rext420-10 the generator starts from conforming Main or Main 10 syntax and rewrites the fields to profile IDC 4, compatibility flag 4, and the general constraints 9F.88 or 9D.88.

For every vector the generator verifies the FFprobe access-unit lengths and I/P types, the VPS and SPS constraint flags, and raw plane fingerprints computed as in production. Without --check, it replaces each committed file once its checks pass. --inspect prints the measured evidence without comparing or writing.

test/capability/HEVCRangeExtensionCapabilities.test.ts verifies the VPS constraint bytes, the intra and one-picture flags, the access-unit lengths, and the I/P slice sequence. Fingerprints use the production 32-bit FNV-1a sampler in capability/CustomDecodeCapabilities.ts: the plane dimensions, then a 64 by 36 uniform grid of samples over each output plane.

Re-encoding with another toolchain may not be byte-identical. Do not update an access-unit length, a constraint string, or a fingerprint until the static vector tests and the decoded raw output have been inspected together.

AV1 Dolby Vision vectors

These test vectors are Dolby Vision Profile 10 in MP4 and in Matroska, one pair per sub-profile: 10.0 (CCID 0), 10.1 (CCID 1, BT.2020 PQ base), 10.2 (CCID 2, BT.709 base), and 10.4 (CCID 4, BT.2020 HLG base). Each is a libaom AV1 Main 10 encode of testsrc2, 192x192 and four frames with a key frame every second frame. Every temporal unit carries one Dolby Vision ITU-T T.35 metadata OBU, and the container signals the configuration record: a dvvC box in a dav1 (10.0) or av01 sample entry, or a Matroska BlockAdditionMapping.

The RPUs are the dovi_tool payloads from src/capability/vectors/test/dolby-vision-rpu/, carried byte for byte as the EMDF payload of the T.35 message:

  • 10.0 alternates profile5.bin and profile5-02.bin;
  • 10.1 and 10.2 use profile8.bin;
  • 10.4 uses profile84.bin.

Each frame’s RPU therefore parses to the same output as the HEVC parse of its source file, which is the known answer. expectations.json records, per vector, the container, sample entry, Dolby Vision configuration, and color, and per frame the source RPU, the key flag, and the SHA-256 of the T.35 message.

FFmpeg’s own AV1 Dolby Vision encoding is not used. Its encoders rebuild each RPU from the decoded metadata, which reorders extension blocks, and its command line cannot signal 10.0, which needs the RPU header when the encoder is set up. Instead the generator inserts the T.35 OBUs after the sequence header, where libaom places metadata, adds a dvvC box to an intermediate MP4, and lets FFmpeg remux that file into both vectors, so FFmpeg writes the container records. It then renames the 10.0 MP4 sample entry to dav1, which FFmpeg cannot write. Before writing, it checks:

  • the RPU and key flag of every temporal unit;
  • the sequence header color;
  • the MP4 sample entry and boxes;
  • what FFprobe reads back from both containers;
  • that FFmpeg parses the same Dolby Vision metadata from each T.35 OBU as from the same RPU carried as HEVC NAL 62.

test/video/dolby-vision/DolbyVisionAV1DemuxIntegration.test.ts opens every vector with Mediabunny, splits each temporal unit with the engine’s splitter, and requires the parser’s packed output to equal the HEVC parse of the source RPU. The vectors prove the demux, the split, and the parse; they prove nothing about decode or presentation.

Local playback media

These write media for smoke tests through a host in a real browser. The generate_ scripts write to the ignored bin/playback_smoke_media/ unless given --output-directory, and the create_ scripts write to the output path they are given. Real playback evidence comes from the host, not from the checks above.

Tests

Most scripts have a test module in scripts/codec_vector_assets/test/; the DTS, TrueHD, 7.1 downmix reference, and JPEG 2000 generators have none. A test adds the generator folder to the import path, so it also runs on its own:

python scripts/codec_vector_assets/test/generated_output_test.py
