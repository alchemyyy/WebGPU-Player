# Codec vectors

A codec vector is a known input with a known answer.
Qualification vectors ship to the browser, where the capability probes check decoders against them before a route is advertised.
Test vectors only feed tests and generators.

The generators are Python 3.10 or later, in `scripts/codec_vector_assets/`, with their tests in `scripts/codec_vector_assets/test/`.
They write the committed `bin/codec_vector_assets/`, except the local playback media generators, which write the ignored `bin/playback_smoke_media/`.
A `generate_` script makes its output from nothing but the repository and FFmpeg, while a `create_` script derives it from media you supply.
Hand-made vectors live in `src/capability/vectors/`.

## Generate or check everything

From the engine root:

```sh
python scripts/generate_all_codec_vector_assets.py            # Writes bin/codec_vector_assets/
python scripts/generate_all_codec_vector_assets.py --check    # Fails unless every committed asset matches
python -m unittest discover -s scripts/codec_vector_assets/test -p "*_test.py"
```

`generate_all_codec_vector_assets.py` runs every generator of committed assets in order, and passes `--regenerate-sources` to the TrueHD generator so its source streams are re-encoded and compared too.
It continues past a failure and exits with status 1 if any generator failed.
It does not run the local playback media generators.

`bin/codec_vector_assets/` is the one committed folder in `bin/`, so every change to an asset shows in review.
`.gitattributes` stores it without line-ending conversion, so the committed bytes are the generated bytes.

Every committed asset reproduces with FFmpeg and FFprobe `2026-03-01-git-862338fe31-full_build-www.gyan.dev` on PATH.
The HEVC range-extension, AV1 Dolby Vision, HDR10+ AV1, and HDR10+ VP9 generators refuse any other build.
The MPEG-2 vector was first encoded by Jellyfin FFmpeg 8.1.2, which writes the same bytes.
Pass another executable to its generator with `--ffmpeg`.

Two helpers serve them: `generated_output.py` (shared write, check, and install helpers) and `engine_layout.py` (the engine's folders, read from `tools/constants.json` through `tools/constants.py`).
The DTS and TrueHD generators compute the TypeScript import paths they embed from the same constants, so moving a folder only needs a rerun.

The AV1 Dolby Vision and both HDR10+ generators take the error they raise, the pinned FFmpeg check, JSON comparison, and bit packing from `media_tools.py`.
Both HDR10+ generators take the HDR10+ frame model, its ITU-T T.35 serialization, and its known answers for `expectations.json` and FFprobe from `HDR10_plus_metadata.py`.

The engine imports the two generated TypeScript modules as `#codec_vector_assets/*`, and `scripts/library-assets.mjs` serves the qualification streams.

The generators work in one of three modes:

- Deterministic generators rewrite their output, and with `--check` fail when a committed file differs from a fresh run: the DTS and TrueHD modules, and the 7.1 downmix reference.
- Encoder-dependent generators compare a fresh encode with the committed bytes: the JPEG 2000 and MPEG-2 vectors, and the TrueHD source streams under `--regenerate-sources`.
  Another encoder build writes different bytes, so a differing encode never replaces a committed asset, while a missing one is installed.
  With `--check`, a missing asset fails as well.
- The HEVC range-extension, AV1 Dolby Vision, HDR10+ AV1, and HDR10+ VP9 generators refuse any FFmpeg build but the pinned one.
  Before writing each encode the HEVC generator checks the access-unit lengths, the picture types, the profile and constraint flags of the VPS and SPS, and the decoded fingerprints.
  The AV1 Dolby Vision generator runs the checks listed in [AV1 Dolby Vision vectors](#av1-dolby-vision-vectors), the HDR10+ AV1 generator those in [HDR10+ AV1 vectors](#hdr10-av1-vectors), and the HDR10+ VP9 generator those in [HDR10+ VP9 vectors](#hdr10-vp9-vectors).

## HEVC range-extension vectors

These Annex B files are deterministic WebCodecs capability probes.
They are 192x192, because common NVIDIA HEVC decoders reject smaller coded sizes.
They prove only that the exact codec configuration decodes, copies to the expected WebCodecs raw format, and produces the expected fingerprints.
They prove nothing about performance, resolution or level limits, seeking, or transport.

Toolchain: FFmpeg `2026-03-01-git-862338fe31-full_build-www.gyan.dev`, libavcodec `62.24.100`, libx265 `4.1+225-1b48507eb`.

The source is FFmpeg `testsrc2` at 192x192 and one frame per second.
Each of the nine vectors is one IDR access unit followed by one P access unit, which qualifies general inter decode for the exact tuple.

Every vector uses these x265 settings, serial because there is no thread pool and one frame thread:

```text
-preset fast -crf 32
-x265-params info=0:pools=none:frame-threads=1:wpp=0:log-level=error:keyint=30:min-keyint=30:scenecut=0:bframes=0:repeat-headers=1
```

`info=0` prevents the x265 user-data SEI, so nothing is stripped after encoding.
For example:

```sh
ffmpeg -f lavfi -i "testsrc2=size=192x192:rate=1:duration=2" \
  -frames:v 2 -pix_fmt yuv422p10le -c:v libx265 \
  -profile:v main422-10 -preset fast -crf 32 \
  -x265-params "info=0:pools=none:frame-threads=1:wpp=0:log-level=error:keyint=30:min-keyint=30:scenecut=0:bframes=0:repeat-headers=1" \
  -f hevc -y main422-10.hevc
```

After each encode the generator rewrites the profile, tier, and level fields of the VPS and SPS, removing and reinserting the emulation-prevention bytes around the rewritten RBSP:

- Level: every vector signals Level 3.1 (`general_level_idc` 93).
  x265 gets no `level-idc`, because with CRF it would enforce the level through VBV, which it reports as non-deterministic.
  Without it x265 signals Level 1 and the slices are byte-identical, so the generator writes 93 instead.
- Profile: x265 does not emit general profile IDC 4 for 4:2:0 at 8 or 10 bits, so for `rext420-8` and `rext420-10` the generator starts from conforming Main or Main 10 syntax and rewrites the fields to profile IDC 4, compatibility flag 4, and the general constraints `9F.88` or `9D.88`.

| File | Pixel format | x265 profile |
| --- | --- | --- |
| `rext420-8.hevc` | `yuv420p` | `main`, rewritten |
| `main422-8.hevc` | `yuv422p` | `main422-10` |
| `main444-8.hevc` | `yuv444p` | `main444-8` |
| `rext420-10.hevc` | `yuv420p10le` | `main10`, rewritten |
| `main422-10.hevc` | `yuv422p10le` | `main422-10` |
| `main444-10.hevc` | `yuv444p10le` | `main444-10` |
| `main12-420.hevc` | `yuv420p12le` | `main12` |
| `main422-12.hevc` | `yuv422p12le` | `main422-12` |
| `main444-12.hevc` | `yuv444p12le` | `main444-12` |

For every vector the generator verifies the FFprobe access-unit lengths and I/P types, the VPS and SPS constraint flags, and raw plane fingerprints computed as in production.
Without `--check`, it replaces each committed file once its checks pass.
`--inspect` prints the measured evidence without comparing or writing.

`test/capability/HEVCRangeExtensionCapabilities.test.ts` verifies the VPS constraint bytes, the intra and one-picture flags, the access-unit lengths, and the I/P slice sequence.
Fingerprints use the production 32-bit FNV-1a sampler in `capability/CustomDecodeCapabilities.ts`: the plane dimensions, then a 64 by 36 uniform grid of samples over each output plane.

Re-encoding with another toolchain may not be byte-identical.
Do not update an access-unit length, a constraint string, or a fingerprint until the static vector tests and the decoded raw output have been inspected together.

## AV1 Dolby Vision vectors

These test vectors are Dolby Vision Profile 10 in MP4 and in Matroska, one pair per sub-profile: 10.0 (CCID 0), 10.1 (CCID 1, BT.2020 PQ base), 10.2 (CCID 2, BT.709 base), and 10.4 (CCID 4, BT.2020 HLG base).
Each is a libaom AV1 Main 10 encode of `testsrc2`, 192x192 and four frames with a key frame every second frame.
Every temporal unit carries one Dolby Vision ITU-T T.35 metadata OBU, and the container signals the configuration record: a `dvvC` box in a `dav1` (10.0) or `av01` sample entry, or a Matroska BlockAdditionMapping.

The RPUs are the dovi_tool payloads from `src/capability/vectors/test/dolby-vision-rpu/`, carried byte for byte as the EMDF payload of the T.35 message:

- 10.0 alternates `profile5.bin` and `profile5-02.bin`;
- 10.1 and 10.2 use `profile8.bin`;
- 10.4 uses `profile84.bin`.

Each frame's RPU therefore parses to the same output as the HEVC parse of its source file, which is the known answer.
`expectations.json` records, per vector, the container, sample entry, Dolby Vision configuration, and color, and per frame the source RPU, the key flag, and the SHA-256 of the T.35 message.

FFmpeg's own AV1 Dolby Vision encoding is not used.
Its encoders rebuild each RPU from the decoded metadata, which reorders extension blocks, and its command line cannot signal 10.0, which needs the RPU header when the encoder is set up.
Instead the generator inserts the T.35 OBUs after the sequence header, where libaom places metadata, adds a `dvvC` box to an intermediate MP4, and lets FFmpeg remux that file into both vectors, so FFmpeg writes the container records.
It then renames the 10.0 MP4 sample entry to `dav1`, which FFmpeg cannot write.
Before writing, it checks:

- the RPU and key flag of every temporal unit;
- the sequence header color;
- the MP4 sample entry and boxes;
- what FFprobe reads back from both containers;
- that FFmpeg parses the same Dolby Vision metadata from each T.35 OBU as from the same RPU carried as HEVC NAL 62.

`test/video/dolby-vision/DolbyVisionAV1DemuxIntegration.test.ts` opens every vector with Mediabunny, splits each temporal unit with the engine's splitter, and requires the parser's packed output to equal the HEVC parse of the source RPU.
The vectors prove the demux, the split, and the parse; they prove nothing about decode or presentation.

## HDR10+ AV1 vectors

These test vectors are one AV1 Main 10 encode in BT.2020 PQ, in MP4 (`hdr10plus.mp4`) and in Matroska (`hdr10plus.mkv`).
It is a libaom encode of `testsrc2` with the settings of the AV1 Dolby Vision vectors, 192x192 and six frames with a key frame every third frame.
The generator writes every metadata payload itself, field by field, and inserts the metadata OBUs before each temporal unit's frame, where libaom places metadata:

- each key frame's unit carries a mastering display color volume (MDCV) OBU and a content light level (CLL) OBU: BT.2020 primaries, a D65 white point, 1000 and 0.005 nits, MaxCLL 940, and MaxFALL 410;
- the first, second, and sixth units carry a profile B HDR10+ ITU-T T.35 OBU, each with its own curve, targeted display, and distribution;
- the fourth unit carries a profile A HDR10+ OBU, without a curve and with a targeted display of 0, whose message ends in a zero byte that must stay when the trailing bits are removed;
- the third and fifth units carry no HDR10+.

FFmpeg muxes the stream into the MP4 and remuxes the MP4 into Matroska.
Both keep the metadata OBUs in each sample, and the `av1C` record FFmpeg writes repeats the first unit's MDCV and CLL OBUs.
`expectations.json` records the color, the coded MDCV and CLL values, and per frame the key flag, whether its unit carries MDCV and CLL, the coded HDR10+ values, and the T.35 message without its trailing bits.

Before writing, the generator checks:

- the metadata OBUs of every temporal unit, read back from the stream;
- the codec, color, packet sizes, and key flags FFprobe reads from the stream and from both containers, and that neither container carries static HDR metadata of its own;
- the side data FFmpeg decodes for every frame of both containers, the independent oracle: libdav1d reports the MDCV and CLL on every frame from the first key frame on, and HDR10+ only on the frame whose unit carries it.

`test/video/hdr/AV1HDR10PlusDemuxIntegration.test.ts` reads both vectors with Mediabunny's `EncodedPacketSink` and requires the engine's extraction and static scan to read every frame as recorded.
`test/pipeline/CustomDecodeWorkerAV1Route.test.ts` plays them through the worker with a stand-in WebCodecs decoder, and requires every posted frame to carry its recorded HDR10+ result.
The vectors prove the demux, the extraction, and the routing; they prove nothing about decode or presentation.

## HDR10+ VP9 vectors

These test vectors are one VP9 Profile 2 encode, 10-bit in BT.2020 PQ, in WebM (`hdr10plus.webm`) and in Matroska (`hdr10plus.mkv`).
It is 192x192 at 24 frames per second, eight frames with a key frame every fourth frame, and each group of four frames is one cluster.
VP9 has no metadata of its own, so each frame's HDR10+ is an ITU-T T.35 message in a BlockAdditional of its block, under FFmpeg's BlockAddID 4:

- the first, second, sixth, seventh, and eighth frames carry profile B metadata with different curves, targeted displays, and distributions, up to 15 percentiles and 15 anchors, and the last two are identical;
- the fourth frame carries profile A metadata, without a curve and with a targeted display of 0;
- the third frame and the second key frame carry none.

Toolchain: the pinned FFmpeg, with libx265 `4.1+225-1b48507eb` and libvpx `v1.16.0-56-g4fcebeabe`.
FFmpeg writes it all:

1. libx265 encodes `testsrc2` with one `dhdr10-info` entry per frame, so FFmpeg decodes HDR10+ frame side data.
2. The `sidedata` filter deletes that side data from the frames without HDR10+, and `setparams` tags every frame BT.2020 PQ, because libvpx-vp9 keeps HDR10+ only when the encoder opens on a PQ transfer, which it reads from the first frame.
3. libvpx-vp9 encodes Profile 2 in one thread, without lookahead or alternate reference frames, so every packet is one shown frame, and passes each frame's HDR10+ to its packet.
4. The WebM muxer writes each packet's HDR10+ as a BlockAdditional, without a BlockAdditionMapping, which WebM does not have.
5. FFmpeg remuxes the WebM into Matroska, which adds the BlockAdditionMapping of BlockAddID 4 to the ITU-T T.35 type.

`expectations.json` records the color, and per frame the key flag, the coded HDR10+ values, and the BlockAdditional bytes.

Before writing, the generator checks:

- every block's BlockAdditionals, read back with its own EBML walk, against the frame's ST 2094-40 serialization in `HDR10_plus_metadata.py`, and the DocType, Colour, BlockAdditionMapping, key frames, and clusters of each container;
- the codec, profile, color, key flags, and HDR10+ side data FFprobe reads from every packet of both containers, the independent oracle.

`test/video/MatroskaBlockAdditions.test.ts` reads both vectors through the engine's Mediabunny hook, and fails when Mediabunny's internals no longer let it read every block's additions as recorded.
`test/video/hdr/HDR10PlusVP9DemuxIntegration.test.ts` plays both through the owned VP9 path with a stand-in decoder, from the start and from the second key frame, and requires every frame's HDR10+ result to be the recorded one.
`test/pipeline/CustomDecodeWorkerOwnedVP9.test.ts` plays them through the worker with a stand-in WebCodecs decoder, and requires every posted frame to carry its recorded HDR10+ result.
The vectors prove the demux, the hook, the extraction, and the routing; they prove nothing about decode or presentation.

## Local playback media

These write media for smoke tests through a host in a real browser.
The `generate_` scripts write to the ignored `bin/playback_smoke_media/` unless given `--output-directory`, and the `create_` scripts write to the output path they are given.
Real playback evidence comes from the host, not from the checks above.

| Script | Writes |
| --- | --- |
| `generate_playback_smoke_media.py` | HDR10 and HLG HEVC Main 10 playback media, and audio-switch variants |
| `generate_static_HDR_validation_vectors.py` | Static HDR validation media |
| `generate_native_HEVC_High_Tier_validation_vector.py` | A native HEVC High Tier stream |
| `generate_dolby_vision_AV1_playback_media.py` | 1080p Dolby Vision Profile 10 AV1 with stereo AAC, per sub-profile, in MP4 and Matroska. The RPUs do not describe the test pattern, so the files prove only that the pipeline runs |
| `create_separate_track_dolby_vision_vector.py` | From an interleaved Profile 7 Matroska: one BL track, and one Profile 7 EL and RPU track |
| `create_dual_track_dolby_vision_MP4_vector.py` | From the separate-track output: an MP4 with a base HEVC track and a dependent `dvh1` or `dvhe` enhancement track |
| `create_profile7_playback_vector.py` | From the separate-track output: a dual-track MP4 for full playback tests. Its BL is scaled to 1080p and re-encoded, so it is no color reference |
| `create_dual_PID_dolby_vision_TS_vector.py` | From a two-track Profile 7 file: a dual-PID MPEG-TS whose EL entry carries a Profile 7 dependency descriptor |
| `create_container_only_HVCE_vector.py` | A Matroska copy whose wrapped EL parameter sets are replaced by filler, so the EL decodes only from the container's `hvcE` |

The `create_` scripts transform a Profile 7 source you supply.
They and both AV1 Dolby Vision generators take an option for each tool they run: FFmpeg and FFprobe from `--ffmpeg` and `--ffprobe` or PATH, and MKVToolNix from `--mkvtoolnix-directory`, then `%ProgramFiles%\MKVToolNix` on Windows, then PATH.
`create_container_only_HVCE_vector.py` rewrites the Matroska file itself and runs no tool.
`media_tools.py` holds that lookup, the bounded tool runner they share, and a check that refuses an output path naming the input file, by case variant or link included.

## Tests

Most scripts have a test module in `scripts/codec_vector_assets/test/`; the DTS, TrueHD, 7.1 downmix reference, and JPEG 2000 generators have none.
A test adds the generator folder to the import path, so it also runs on its own:

```sh
python scripts/codec_vector_assets/test/generated_output_test.py
```
